# 产品循环与交接

## 建立蓝图

先复用已有 PRD 和项目，不因为加载技能另建工程。新想法可先形成待确认需求和方案草稿；确认目标、边界及重要未知后再形成实现交接。

工作台内可使用独立文件 `PRD.md`、`Agent方案.md`、`Agent迭代记录.md`、`Agent验证报告.md`，按已有命名调整。需要保留已批准版本时，通过审阅新增 `PRD-V1.md` 等快照，不覆盖旧版；不要强制创建原引擎的 out/、plan.json 或 skeleton/ 目录。

## 新需求

1. 读当前 PRD、方案和最近的验证结论。辨认是新增、改变、移除还是澄清，标明用户来源。
2. 比较目标、范围、数据和权限影响；列出组件由什么决定变成什么决定，以及原因和迁移风险。
3. 提交 PRD 与方案的修改候选；用户尚未批准时标为草稿，不擅自提升批准版本。
4. 生成最小增量待办和回归计划。保留原有实现与用户修改，不为适配方法重建项目。
5. 分别记录自动化检查、真实运行结果与人工验收。只有用户实际确认后才记录人工结论；未运行的保持待验。

迭代记录至少包含日期、本轮需求、来源、受影响文件、选型变化、待办、已知风险、验证结果和下一步。没有代码执行能力时，待办是交接清单而非已经执行的修改。

## 原引擎与本技能的区别

原项目可通过 init / plan / verify / revise 管线创建版本快照和结构化结果；这里使用当前工作台会话按方法分析，不声称运行过这些命令。用户另行要求调用原引擎时，先确认其实际安装位置、可用环境、成本与输出范围，遵循原引擎说明；不假定用户文件夹名或安装状态不变，不自动安装依赖或再配置一个模型。

任何中断后的继续都从已确认文件和证据恢复；不能反复付费重试绕过原预算，也不能把未完成的方案标为已验证。
