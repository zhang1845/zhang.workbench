# 带证据的差距检查

## 限定检查对象

先确认用户给出的项目和 PRD。只读其明确放入范围的材料；不搬动外部项目、不扫描密钥文件、不默认把整库发给另一个模型。无代码权限或没有源码时，交付材料级检查并说明限制，不把未读文件判成缺失。

有 PRD 时以 PRD 为基准；没有时从 README、入口和用户链路形成反推需求草稿，逐项标注推断并请用户确认。模板、示例代码和依赖包存在，不代表产品已接入这些能力。

## 证据分级

沿主入口、工具注册、权限检查、状态持久化和测试追踪实际调用，按需对照[组件表](design.md)。每条记录：需求 / 组件、位置（文件与行号或文档章节）、观察结果、影响、验证建议。

- **已找到实现线索**：指出实际调用与测试；不据此保证线上可用。
- **薄弱**：有实现但覆盖不完整，说明具体缺口。
- **未找到线索**：写明已查范围；不能直接宣称全库没有实现。
- **确认缺失**：只有检查了相关路径并有足够证据时使用。
- **无法判断 / 不适用**：保留未知，或说明 PRD 没有触发该机制。

按真实损失、需求影响和修复依赖给出先补什么，不把所有缺口都标最高优先级。关键词命中只是检索入口；覆盖比例不是安全评分、功能完成度或真实验收通过率。

## 交付与复核

交付差距表、优先修复建议、可复现的验证步骤、尚未覆盖的范围；必要时附反推 PRD 草稿。核对每条高风险结论是否有证据、已有线索是否被漏掉、组件必要性是否来自产品任务。

仅做检查时不修改代码或配置。没运行测试就写未运行；工具受限时交接验证清单，不伪造日志、截图或人工验证结论。没有独立审阅者时报告只写自查结果。
