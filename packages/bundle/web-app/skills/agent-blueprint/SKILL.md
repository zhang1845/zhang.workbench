# Agent 产品蓝图

从用户确认的任务出发，判断模型之外需要什么工具、知识、观察、行动接口与权限。使用当前会话已配置的模型分析，不要求另配 API Key，不运行原项目的 Python 管线。

## 识别本轮工作

先读当前项目已有 PRD、方案、状态及本轮输入，复用已确定的范围和技术约束。选择一个入口，不把单次分析扩成完整开发：

- **新方案**：想法或 PRD → 事实与待确认 → 五要素 → 组件取舍 → 架构方案。读取[方案与选型](references/design.md)。
- **查差距**：用户指定的现有项目与 PRD → 实现证据 → 缺口与验证建议。读取[差距检查](references/audit.md)；未授权访问源码时只能检查提供的材料。
- **迭代**：新需求 → PRD 与选型差异 → 增量待办及验证计划。读取[产品循环](references/iteration.md)。

输入是普通非 Agent 产品时说明这套蓝图的适用边界，不为套方法引入 Agent loop。只问会改变方案、数据边界、预算或交付范围的缺口，允许用户暂不确定。报告明确区分原文事实、确认决定、假设、推断与未知。

## 方案和证据标准

每个组件都对应需求证据，标注必选、二期、待确认或放弃；未提及不等于不需要。逐项判断而非把 17 个组件全部安装。七层图可以写 N/A，不为补齐图形增加系统。

先交方案；生成或修改产品代码须有用户明确要求与适用的执行环境。新需求先更新需求与取舍，再提出增量实现，不重建已有项目、不覆盖用户手改内容。

完成报告前自查事实依据、组件选择、工具副作用、权限与失败降级、验收办法。没有另一个真实审阅者时只称自查，不编造独立审稿、运行结果、调用次数或 Token 用量。静态信号覆盖率不是功能完成率；人工验收结论只能记录用户实际反馈。

## 工作台中的文档操作

工作台的文档项目仅支持当前项目根目录内独立的 Markdown 或文本文件，通过 read / write / edit 提交修改审阅；确认前不声称已保存。可用 `Agent方案.md`、`Agent差距报告.md`、`Agent迭代记录.md` 等文件名，已有命名优先沿用。需要 PRD 快照时采用新文件名，不覆盖旧版。

这里只加载工作方法，不新增代码执行权限。受文档模式限制时交付可审阅方案或开发交接清单，明确代码与运行验证尚未执行；不通过 shell、脚本或其他工具绕过审阅。仅讨论不创建文件。不会写入原始项目目录，也不要求把目标项目搬到原引擎的 out/ 下。不得因加载技能而发布、部署、联系他人或创建计费资源。
