# 阶段闸门与证据包

## 判定规则

每个当前阶段的检查项记录通过、未通过、待验或 N/A，附真实依据。N/A 要说明原因；未通过或待验时可以交付明确标注的阶段成果，不能宣布该阶段已经通过。文档或技术适配阶段不强求运行不存在的代码。

| 检查项 | 如何核对 |
| --- | --- |
| 当前范围 | 对照已批准目标和不做项，没提前扩展后续阶段 |
| 自动化 | 相关测试实际执行的通过数/总数与未覆盖范围 |
| 模型能力 | 新增/改变的模型契约有真实端到端证据；无 Key 则待验，纯工程变更可说明 N/A |
| 工程检查 | 按现有技术栈做相关类型、Lint、构建检查；尚无代码则 N/A |
| 秘密与数据 | 秘密未进入仓库、前端或交付包，隐私边界有依据 |
| 持久化 | 需要保留的数据/任务/人工确认点重启后实际恢复；无执行能力则待验 |
| 界面 | 有界面则检查目标尺寸、核心操作和错误恢复，无界面则 N/A |
| 使用说明 | 当前启动、配置与验证说明与实测一致 |
| 项目状态 | 候选修改经界面确认保存；不是只写了草稿 |
| 证据包 | 有实际可查看的材料或明确未完成项 |

## 用户证据与技术记录

用户证据优先包括关键页面/接口结果截图、实际可打开地址或逐步操作说明、上述阶段闸门。技术命令、日志和详细覆盖范围另作可追溯记录，需要时可查看，不隐藏失败。

工作台文档项目只保存根目录的 Markdown/文本；可以用 `阶段2-验收.md` 链接已有证据或记录截图位置，不为了套原手册创建嵌套目录、复制用户原始文件或绕过审阅写入二进制。截图不能取得时明确标注，不虚构。

阶段交付用简短结论说明完成的部分、未通过/待验项、原因与下一步由谁做什么。用户接受风险的阶段性成果也不等于缺失验证已经通过。
