# 技术适配与真实验证

## 先看现状

有工程访问权限时，先查项目规则、README、依赖和启动方式、相关代码/测试、未提交修改与数据位置。不先重构，不要求项目改成手册目录。环境检查仅限目标项目需要的工具；文档阶段不强制安装 Python、Node 或原工具包。

把选择分成三层：安全与数据保护底线；结合项目的默认方案；被需求触发的按需模块。已有框架优先沿用。新项目给一个有依据的推荐，具体库版本、服务能力和费用在真正选用时查官方现行文档，不照搬来源手册的版本号。

## 技术适配声明

至少说明：

1. 产品任务、主要交互、当前阶段范围；选择后端先行还是纵向切片及原因。
2. 采用的现有/默认方案，以及数据库、检索、队列、OCR、流式等按需模块各自由什么要求触发。没有需求不预装。
3. 暂缓或偏离项、代价和再次评估条件；涉及数据迁移、隐私、费用或交付终端变化时等待确认。
4. 密钥、持久化、输入输出校验、失败降级、日志、预算与验证的设计及待处理项。
5. 用户需要决定的事项。用产品语言确认理解是否正确、有无新增费用/数据上传/范围、暂缓项是否影响验收。

只做设计时这些是拟议方案，不是已经通过的工程检查。

## 实现交接检查

按当前阶段记录目标、范围与不做项、状态流转、数据、接口/工具、Prompt、权限、失败处理、测试和启动/回退办法。工作台不能执行工程任务时交接这些内容，不把它写成已实现。

- 输入和模型输出需要结构校验，区分语法解析失败与业务质量瑕疵；不为数量/文风不符无限重试。
- 模型配置沿用用户选择，设置有限重试、超时、步数和成本边界；包含客户端初始化失败的处理。
- 长任务与人工确认点可持久化恢复；文件式状态考虑 schema、原子写入、损坏处理和并发边界。
- 固定流程可由确定性状态机编排；动态工具选择才需要受限 Agent 决策。高风险动作仍由代码和人工审批约束。
- API 明确请求、响应与错误；使用 SSE 时覆盖正常结束和错误结束，不以静默断流冒充完成。沿用已有协议，不为套模板破坏兼容。
- 上传校验格式、真实类型、大小、安全文件名；日志只记必要的调用元信息，不记录秘密或完整敏感文档。

## 双层验证

**离线自动化**覆盖本轮相关的业务逻辑、状态流转、权限、解析和错误路径，使用项目已有工具。测试范围与改动风险匹配，不为流程完整强跑无关全库测试。

**真实模型冒烟**用于本轮新增或改变的模型调用契约及关键用户链路：真实输入 → 模型 → 存储/返回 → 可查看结果。覆盖认证、真实输出、时延与流式结束，报告模型、时间、实际可取得的用量与结果。只有实际获得用量才能写 Token 或成本；不能用示例数冒充实测。

无真实 Key、用户未同意调用费用或执行环境受限时，记待验并说明怎样补验。已测契约复用时说明覆盖关系，不机械重复付费调用；纯工程变更不因套流程再调用真实模型。

效果标准不足时，可提议用 5–10 条真实样例、至多 5 个业务维度让负责人评分，保留不可接受项，由其确认门槛。样例产生前先确认数据和费用，不把打分示例当成项目通过线。分别记录格式合规、内容质量、数量约束与人工判断。

最终按[阶段闸门](gates.md)报告已通过、未通过与未覆盖范围。模拟数据和原型可以推进，不等于真实链路已验证。
